## Codebase Patterns
- Backend lives in `backend/` (Python/FastAPI + SQLAlchemy 2.0 + Alembic + PostgreSQL). Repo root has no top-level src; each subsystem gets its own folder (`backend/`, later `frontend/`).
- Python venv is at `backend/.venv` (gitignored). Activate with `source backend/.venv/Scripts/activate` (Git Bash on Windows) before running pip/alembic/ruff/mypy.
- DB config is env-driven: `backend/app/config.py` reads `DATABASE_URL` from `backend/.env` (gitignored; `.env.example` is committed as the template). Local Postgres 18 is running as a Windows service; `postgres`/`postgres` is the local dev superuser login (databases: `finance_invoice_approval` for dev, `finance_invoice_approval_test` for tests).
- SQLAlchemy models live in `backend/app/models.py` on a shared `Base` from `backend/app/database.py`. Alembic's `migrations/env.py` imports `app.models` and sets `target_metadata = Base.metadata` so `alembic revision --autogenerate` picks up model changes automatically. `env.py` also overrides `sqlalchemy.url` from `app.config.settings` at runtime, so `alembic.ini`'s `sqlalchemy.url` is intentionally left blank.
- Gotcha: Postgres ENUM columns (SQLAlchemy `Enum`) are NOT dropped automatically by `op.drop_table` when the enum is shared across multiple tables (autogenerate's downgrade only drops tables). Any migration that creates a `sa.Enum` must add explicit `sa.Enum(name='...').drop(op.get_bind(), checkfirst=False)` calls at the end of `downgrade()`, after all tables using that enum are dropped — otherwise re-running upgrade after downgrade fails with `DuplicateObject: type "..." already exists`. Verified by round-tripping upgrade -> downgrade -> upgrade.
- Lint/typecheck tooling: `backend/requirements-dev.txt` adds `ruff` and `mypy` on top of `requirements.txt`. Run `ruff check app migrations` and `mypy app` from `backend/` (with venv active) as the "typecheck/lint passes" gate for backend stories.
- Enum/status defaults: model-level Python `default=` (SQLAlchemy-side) is paired with `server_default=` (DB-side) so both ORM inserts and raw SQL/direct DB writes get the same default (e.g. `User.role` defaults to `requester`, `Request.status` defaults to `pending`).
- App structure: `backend/app/main.py` is the FastAPI entrypoint (`uvicorn app.main:app`); route handlers live in `backend/app/routers/<name>.py` as `APIRouter` instances included from `main.py`; cross-cutting business logic (email, file storage, etc.) goes in `backend/app/services/<name>.py`. `app/models.py` stays SQLAlchemy-only.
- `backend/app/config.py`'s `Settings` class is the single source of truth for all env-driven config (DB URL, SMTP, upload dir, file size/count limits) — add new settings there with an `os.getenv(..., default)` fallback, and mirror the key in both `.env` and `.env.example`.
- Auth stack: password hashing uses `bcrypt` directly (`app/security.py`: `hash_password`/`verify_password`), JWTs use `pyjwt` (`create_access_token`/`decode_access_token`), signed with `settings.jwt_secret_key`/`jwt_algorithm`/`jwt_expire_minutes` (env-driven, added to config.py). Pydantic request/response models live in `app/schemas.py` (uses `EmailStr`, which requires the `email-validator` package alongside `pydantic`).
- Test setup: pytest + httpx (for FastAPI's `TestClient`) live in `requirements-dev.txt`. `backend/tests/conftest.py` points at a separate `finance_invoice_approval_test` Postgres DB (override via `TEST_DATABASE_URL` env var), creates all tables once per test session via `Base.metadata.create_all`, and gives each test function an isolated DB transaction (`db_session` fixture: begin -> yield -> rollback -> close) so tests never leak data between each other. The `client` fixture overrides FastAPI's `get_db` dependency with `db_session` and returns a `TestClient`. Run tests with `pytest` from `backend/` (venv active) as the "Tests pass" gate.
- Gotcha: `.env` (gitignored, local-only) can get modified outside of an iteration (e.g. by the user or a hook rewriting SMTP addresses) between when you edit it and when you check it later — always re-read `.env` right before relying on it if some time has passed, and re-apply any settings your story added rather than assuming your earlier edit still stands. This never affects commits since `.env` isn't tracked.
- Auth/RBAC dependencies live in `backend/app/dependencies.py`: `get_current_user` (FastAPI dependency, reads `Authorization: Bearer <jwt>` via `fastapi.security.HTTPBearer(auto_error=False)`, decodes with `app/security.py`'s `decode_access_token`, looks up the user by the `sub` claim, raises 401 on missing/invalid/expired token or unknown user id) and `require_finance_user` (wraps `get_current_user`, raises 403 unless `role == UserRole.finance`). Future protected routes should depend on these via `Depends(get_current_user)` / `Depends(require_finance_user)` rather than re-implementing auth checks. Because FastAPI `Depends(...)` default args are plain function defaults, these dependency functions can also be called directly (not just through FastAPI's DI) in unit tests, passing an `HTTPAuthorizationCredentials` or `User` instance by hand — no need to spin up test endpoints just to unit test a dependency.
